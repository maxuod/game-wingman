# 产品定义 v0.2

日期：2026-09-24（America/Halifax）。状态：用户已明确实验样品与 GitHub 反馈方向；Electron 桌面主窗口和独立浮窗已实现，识别与攻略检索尚未接入。UI 以简洁、清楚为第一优先级。

## 1. 用户已经明确的需求

- 产品形态：AI 游戏攻略助手。
- 桌面平台：Windows 与 macOS。
- 信息输入：读取屏幕中的游戏信息。
- 知识来源：从数据库检索所需攻略。
- 展示方式：游戏旁的浮窗。
- 首个游戏：TFT；长期结构应能扩展到其他游戏。
- 产品阶段：试用品，以 TFT 为技术样板，保留屏幕读取和动态攻略提示的原始目标。
- 发布目的：通过 GitHub 展示样品、收集反馈，为后续更多游戏产品提供基础。
- 使用说明：明确实验性质与可能的账号处罚、封号风险。
- 数据范围：美服 NA 正式服为准，优先最新补丁和热修；游戏实体采用英文数据，UI/UX 独立原创。

## 2. 产品体验建议

主窗口负责游戏选择、攻略管理、截图来源、权限和设置；浮窗负责短内容阅读。

每次输出包括：相关知识、适用条件、解释、来源和适用补丁。主视图最多放三张简短卡片，细节展开查看。玩家能够收起、拖动、锁定位置、临时交互和一键隐藏浮窗。

识别不确定时显示待确认字段；未找到适用攻略时明确显示没有匹配结果。不要让语言模型把不确定的截图内容、旧版本攻略或模型常识包装为当前事实。

界面暂按中文设计，实体以美服英文名称和稳定 ID 为基准，中文作为显示别名。地区已确定为美服 NA 正式服，受众水平待定。当前赛季和补丁通过数据核查确定，不将 TFT、国服云顶之弈和金铲铲视为同一数据及政策环境。当前重点是获得试用反馈，付费、账户系统和商业发行不纳入首个样品。

## 3. TFT 政策事实与样品范围

2026-09-24 查阅的 [Riot TFT 开发者政策](https://developer.riotgames.com/docs/tft#game-policy) 区分了赛前静态资料、赛后学习与根据当前局势动态给出建议。后者受到明确限制，对手侦察也在不批准的用途中。

因此，截图读取方式本身不能证明产品可获批准。依据 [Riot 通用政策](https://developer.riotgames.com/policies/general#product-registration)，面向玩家的产品还涉及登记和审核。

用户已明确以实验样品收集反馈；据此保留实时读取和动态提示的开发方向，不再将静态浮窗或赛后复盘作为首版产品定位。试用品标签、公开源码和封号预警不改变政策事实；技术实现、公开发布状态与官方认可分别记录。公开源码交接不代表官方认可、完成 AI 链路或完成真实游戏验证。

| 场景 | 拟议行为 | 当前判断 |
| --- | --- | --- |
| 屏幕读取 | 用户选择窗口，手动或低频采样并提取可见信息 | 样品核心 |
| 攻略动态提示 | 依据识别信息检索攻略并在浮窗更新解释 | 样品核心；披露现行政策和账号风险 |
| 静态攻略阅读 | 查看手动选择的攻略 | 基础/降级体验 |
| 截图导入 | 用固定样本重复验证识别与检索 | 测试辅助 |
| 赛后学习 | 从已结束对局的画面解释相关攻略 | 可选扩展，不替代实时目标 |

风险文案在 README、试用说明及未来应用首次使用界面保持一致，不宣传“零封号风险”“官方授权”或“保证上分”。具体试用说明见 [usage.md](usage.md)。

## 4. 首个可运行样品

1. **桌面壳和浮窗**：两种窗口、显示/隐藏快捷键、拖动和位置锁定、点击穿透模式。
2. **输入**：用户选定游戏窗口后启动读取，支持单次触发、低频更新、暂停和权限拒绝处理；截图导入用于调试和复现。
3. **TFT 内容识别**：首批只识别英雄名称与装备名称，输出字段级置信度及可编辑结果。图标识别难度单独测量，不承诺 OCR 可以直接解决。
4. **攻略库**：维护小规模、人工审核、来源明确的内容；按游戏、赛季、补丁、语言和实体过滤。
5. **AI 解释**：只依据检索证据解释适用条件与选项；区分画面观察、攻略内容和推断。
6. **状态反馈**：展示输入时间、识别状态、攻略版本和失效状态。过时请求不得覆盖较新的结果。
7. **试用反馈**：提供版本信息、已知限制与 GitHub Issue 入口；由用户主动提交，不自动上传截图或收集游戏账号信息。

优先验证的问题是：能否读准需要的信息、能否找到适用攻略、浮窗是否有帮助，以及哪些模块能直接用于下一款游戏。玩家减少切出游戏查资料并理解攻略条件是待验证假设；GitHub 星标和下载量不单独证明这项价值。

## 5. 内容库方案

- 已核查 ARAM-tool 的接入模式，详见[参考项目审查](data-source-review.md)；TFT 来源以[美服数据源核查](tft-data-sources-2026-09-24.md)为准。UI 采用独立的[原创设计方向](design-direction.md)。
- 实体数据与攻略分开：名称、图标、羁绊等元数据不能替代阵容运营知识。
- 官方静态资产可从 [TFT Data Dragon 文档](https://developer.riotgames.com/docs/tft#data-dragon) 开始评估；其更新可能滞后于补丁，不能仅以下载日期认定适配当前客户端。
- 攻略使用自编、获授权或明确允许使用的材料。记录来源、使用依据、作者、审核日期和有效补丁。
- 初始检索优先使用结构化字段、关键词和实体别名；知识规模及自然语言查询效果需要时再增加向量检索。
- 新补丁到来后重新审核内容；不确定适配范围的旧攻略停止作为默认推荐依据。

## 6. 首次验证的完成条件

- 在 macOS 和 Windows 分别记录启动、浮窗、捕获、显示缩放及权限测试结果。
- 在预先标注的截图样本上逐字段评价准确率、覆盖率和拒答率；报告样本来源及分辨率，不凭几张成功截图声称稳定。
- 截图可校正，所有攻略卡可追溯到数据库条目和来源。
- 没有匹配、错误补丁、低置信度及网络失败均有明确反馈。
- 不抢游戏焦点；穿透模式仍能通过快捷键恢复操作或隐藏。
- 记录端到端延迟、模型调用成本、CPU/内存和游戏帧率变化；先测量再定性能承诺。

- GitHub 发布材料区分已实现功能、示例数据和待实现能力；每个平台单独注明测试状态。
- 收到的问题能够关联应用版本、操作系统、游戏版本和可复现步骤，形成下一轮开发任务。

## 7. 后续需要确定的产品决策

- 首发界面语言和初始测试设备；游戏数据地区已经确定为美服。
- 首批用户的水平与最重要的查攻略场景。
- 可使用的攻略来源及内容维护责任。
- 云端视觉模型、本地识别或混合处理的成本与隐私偏好。

- GitHub 仓库名称、代码许可证和首个发布版本的打包形式。

这些决策不阻碍窗口读取、知识检索与桌面浮窗的基础开发。TFT 只承担首个适配器的角色，公共模块按后续游戏可复用的边界设计。
